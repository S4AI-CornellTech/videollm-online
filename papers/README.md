# Streaming video understanding: paper collection

55 papers: 44 on streaming / online / efficient video LLMs + 1 foundational accelerator paper (main table), 6 long-context LLM inference tools, and 4 VLA memory papers (separate sections), collected for comparing against our fine-tuned VideoLLM-online and for the
DGX Spark profiling (growing KV cache). PDFs are named `<arXiv id>_<name>.pdf`. This folder is git-ignored.

**How the table was filled:** from each PDF's own text (title page, abstract, experiments and implementation sections),
not from memory, except where marked.

- **Year:** first arXiv release (HERMES: publication year, no arXiv version downloaded).
- **Venue:** ✓ = printed in this PDF. † = not printed in this arXiv version; venue from memory, **unverified**. "arXiv" = no venue known.
- **Models:** the base model(s) a method is built on, or for benchmarks the main models evaluated. Most papers also compare many other models; only the main ones are listed.
- **Hardware:** as stated in the paper. "Not stated" means no GPU model is named in the text.
- **Solution tags:** what each paper proposes; see "Solution tags" below the topic tags.
- **Topic tags:** `KV` KV-cache / memory efficiency · `MEM` memory-based streaming · `PRO` proactive "when to speak" · `RT` real-time answering · `OMNI` audio + video · `BENCH` benchmark · `HW` hardware.

**Ranked by relevance to the research question:** *can streaming VQA run infinite videos with bounded memory within an
edge device's fixed memory and power budget, with a small accuracy loss and lower energy than the state of the art?*
The proposed solution is a budget-aware runtime controller over **ingest** (prefill FPS, token pruning, frame compression),
**memory compression** (KV quantization, consolidating old context into text) and **memory movement** (offloading cold
memory, prefetching what will be needed).

- **1–8:** closest prior art: bounded memory on edge hardware with energy measured, KV quantization, memory movement (with prediction), or runtime scheduling of the pipeline.
- **9:** SpAtten, foundational work outside video (adaptive precision and token pruning for text attention).
- **10–28:** each covers one knob of the controller (compression, consolidation, ingest control, budget allocation).
- **29–33:** platform, accuracy baselines and benchmarks for measuring the accuracy cost.
- **34–45:** less related (mostly proactive timing or omni models).

The "Fit to RQ" column names the parts of the proposal each paper covers: **Ingest**, **Compress**, **Consolidate**,
**Move**, **Budget**, **Edge + energy**, or its role as a baseline / benchmark.

**Note: how these differ from the streaming setting** (and what a reviewer comparing against them should hear):

- **The question is known in long-context inference, unknown in streaming.** Query-aware selection (e.g. SnapKV picking the entries the question attends to) isn't available while frames arrive; streaming methods must compress or offload without knowing what will be asked, or retrieve at question time.
- **One large prefill vs thousands of tiny ones.** These tools target one long prompt then decode. Streaming runs an 11-token prefill per frame (VideoLLM-online), which is memory-bound and was ~85% of DGX Spark time in our profile; V-Rex calls this "iterative prefill" unique to streaming.
- **No frame-rate deadline.** Long-context inference optimizes throughput or latency of a request; streaming must also keep up with the incoming frames or fall behind permanently.
- **Unbounded length.** Long-context work extends or fills a context window; streaming must bound memory forever, with mostly irreversible decisions.
- **Fixed policies.** KIVI's bit width, H₂O's budget, StreamingLLM's window and FlexGen's placement are chosen up front; InfiniGen predicts per step but for a fixed prompt. None adapt to a changing memory / power budget over an unbounded stream, which is the proposed controller's contribution.

**Note: what transfers and what differs**

- **Same gap as streaming VQA:** all four are evaluated on datacenter GPUs only (A100 / H100 / A800). None runs on robot hardware (e.g. Jetson Thor / Orin), none measures energy, and their memory sizes are fixed (MemoryVLA capacity, EventVLA N_max, HELM k), not adapted to a memory / power budget at runtime.
- **The task is known:** unlike streaming VQA, the instruction is available from the start, so memory can be chosen with the task in mind (task-aware selection is allowed).
- **Tighter deadlines:** control steps take tens of milliseconds (HELM's memory module alone: 12 ms/step), so the controller's own overhead matters more than at 2 fps VQA.
- **More input per step:** multiple cameras (MEM: 4 streams).
- **Accuracy means task success:** forgetting causes failed or repeated physical actions; evaluation is LIBERO / CALVIN / SimplerEnv / RoboTwin-MeM or real robots, not VQA benchmarks.
- **Possible first experiment:** replace EventVLA's or MemoryVLA's fixed memory cap with the budget-aware controller and evaluate in simulation (LIBERO-LONG or RoboTwin-MeM) on a Jetson.

## Most relevant to our DGX Spark / Jetson findings

- **V-Rex** profiles the same model we use (VideoLLM-online, Llama-3-8B + SigLIP) on COIN, and compares Jetson AGX Orin with A100 for its growing KV cache.
- **InfiniPot-V** runs a capped-memory streaming VLM on a Jetson AGX Orin.
- **StreamingVLM, ReKV, HERMES, StreamKV, LiveVLM, StreamMem** are training-free or light ways to bound or shrink the KV cache that grows with every frame.
- **ShallowStream** and **VideoLLM-MoD** cut per-frame prefill cost by skipping layers.

## Gaps relative to the research question

From the 51 papers (based on reading their text and a keyword scan, so not exhaustive):

- **No paper combines all three knobs** (ingest control, compression and memory movement) in one budget-aware runtime controller. StreamingTOM comes closest (ingest budget + 4-bit memory) but has fixed settings and no memory movement; ViCoStream and StreamAhead coordinate the pipeline for speed, not for a memory / power budget.
- **Energy is measured by only two papers**, InfiniPot-V and V-Rex, both on a Jetson AGX Orin. Everything else reports latency and GPU memory only.
- **KV-cache quantization:** StreamingTOM stores memory at a fixed 4 bits (kept on the GPU), and V-Rex compares against a 4-bit KV accelerator. For text attention, SpAtten (HPCA 2021) already adapts precision at runtime (fetch high bits first, low bits only when confidence is low), but nobody does this for **streaming video KV caches** or under a memory / power budget, or combines it with moving memory between tiers.
- **Semantic consolidation into text is rare**: StreamScout (text timeline) and Response-G1 (scene graphs).
- **Predictive prefetching** (bringing back memory before it's needed) appears only in StreamAgent; ReKV, V-Rex and StreamMem fetch on demand.
- **Ingest control is well covered but static:** token budgets and pruning (StreamingTOM, STC, TimeChat-Online), codec signals (CodecSight, RLT), event gating (StreamMind). The offline ones (RLT, DyCoke, PruneVid) also see the whole clip, and PruneVid the question. DyCoke re-decides per decoding step, but none adjust these rates causally from a memory or power budget.
- **None evaluate a power budget** as a constraint, or decide at runtime how to trade accuracy against memory and energy.
- **Nothing on vision-language-action (VLA) models** for the future-work direction.
